## Summary
This revision represents a substantial and genuine improvement over prior rounds. The authors have successfully separated the join (U0) and meet (U∧) operators, introduced the `UAndOn` family with antitone monotonicity, sharply delimited non-goals, stratified RQ1–RQ6 with explicit primacy for RQ3/RQ4/RQ5, and added the `proj`/`obs`/`extract` composition chain (§2.6) that was the central missing mechanization link. The must/may semantics (§4.7) are now formally stratified with Lean artifacts cited, and the PoC is clearly bounded as a feasibility demonstration (n=3, interval-domain only). Several weaknesses remain that prevent immediate acceptance: (1) §2.4's `UAndOn_antitone` statement is presented without the crucial `active`-as-`Prop` quantifier being made explicit in the prose—readers must infer the coercion from the Lean code; (2) §2.5's two Ω realizations (`Ω_trace`, `Ω_art`) are introduced without a formal separability condition specifying when the same theorem holds for both, leaving an implicit universality claim; (3) §3.5's must-side inclusion chain `U* ∩ Dom_{active} ⊆ U∧_{active} ⊆ U0On(active)` derives the second inclusion from `UAndOn_subset_U0On`, but the paper never explicitly states this as a named lemma—it is only reachable via §3.3's bullet, creating a forward-reference gap; (4) §4.3's "typical proof obligation" block presents the concrete extractor connection steps in an imperative list style that slightly over-promises (the word "典型的" is correct but the numbered steps read as a recipe, not as a non-goal boundary); (5) §4.7's three-table breakdown (judgement / policy_judgement / none_semantics) is internally consistent but the definition of `semanticPullbackMay` given in the margin formula differs in whitespace/layout from the Lean definition in §2.4—minor but can create transcription confusion. None of these are correctness errors; they are exposition and cross-reference precision issues that a careful revision can resolve.

## Required Fixes
- §2.4 / §3.3 cross-reference gap: The second inclusion `U∧_{active} ⊆ U0On(active)` in the chain at §3.5 is attributed to `UAndOn_subset_U0On_of_nonempty_active` only parenthetically in §3.3. Give this lemma its own one-sentence statement in §3.3 (or rename the §3.3 bullet to cite it by name) and add a forward reference in §3.5 of the form '(by Lemma 3.3.1)'. Without this the reader must reconstruct the proof chain manually across two non-adjacent sections.
- §2.5 Ω duality without separability condition: Two distinct root spaces (`Ω_trace`, `Ω_art`) are presented as examples, but no condition is given for when a theorem proved under one realization transfers to the other. At minimum, add a sentence: 'Theorems in §4 are stated for an abstract `α`; both realizations are valid instantiations. Claims about one realization do not transfer to the other without a separate argument.' This prevents a sophisticated reader from inferring a uniformity claim that the paper does not intend.
- §4.3 proof-obligation list style: The numbered steps (1–4) under 'concrete extractor connection' read as a constructive recipe. Prepend with an explicit hedge: 'The following is illustrative of the proof structure a user of this framework would need to supply; it is NOT a proof we carry out in this paper.' The current text says '本稿では未実施' only at item 1, leaving items 2–4 ambiguous.
- §4.7 `semanticPullbackMay` formula alignment: The margin formula for `semanticPullbackMay(E,S)` includes `proj_i(x)=none` as a disjunct, but the Lean definition in §2.4 shows `preimageMay` directly using `M.proj i x = none`. Confirm (or explicitly state) that `E` is not used in the `none` branch of `semanticPullbackMay`—i.e., the `none` disjunct is independent of the abstract relation `E`. If so, state this explicitly ('the `none` branch does not depend on `E`; it represents observational absence, not a semantic judgment about `E`'); if not, the formula is inconsistent with the Lean definition.

## Optional Fixes
- §3.1 `U0On` definition: The prose introduces `U0On(active)` before `U0 := U0On(λi, True)`, which is correct. However, the display math uses `∃i, active(i) ∧ x ∈ lifted(i)` while the Lean `U0` definition uses `∃i : ι, x ∈ M.lifted i` (without an `active` guard). Add a one-line note that `U0` is the special case where `active = fun _ => True`, making `U0On` the general family and `U0` a derived abbreviation—this prevents confusion for readers who read Lean code first.
- §6.3 `support_ratio` vs. observability: The paper correctly states that `support_ratio` is an 'observability index, not a specification satisfaction rate.' Consider promoting this disclaimer to a Definition box (even an informal one) rather than a prose aside, since the metric appears in the results table and reviewers from the SE community may conflate observability with correctness.
- §7.4 theorem count methodology: The counting command `rg -n '^theorem '` will miss `private theorem` and `protected theorem` declarations. If such declarations exist in the Lean files, the reported count of 59 may be understated. Either confirm no private theorems exist or amend the count command to `rg -n '\btheorem\b'`.
- §3.4 MUS definition completeness: The definition of `active' ⊊ active` uses `∀i, active'(i) → active(i)` as the subset direction, which is correct for `Prop`-valued predicates. However the existential witness `∃j, active(j) ∧ ¬active'(j)` should be stated in a constructive-logic note if the paper targets a Lean4 audience, since `¬active'(j)` is classical. Add '(uses classical negation; consistent with `Classical.em` in Lean4)'.
