## Summary
The core offline replay pipeline is structurally sound: `reproduce.sh` performs SHA256 pre-checks on two key files, invokes three deterministic replay modes, and the primary execution log (`external_validation_graceful_may.log`) matches all four paper-claimed acceptance criteria exactly. The lock file (`external_validation_sources.lock.json`) records 9 URL→SHA256→snapshot mappings, and offline mode verifies each snapshot's hash before use. However, two specific replay blockers prevent unconditional gate passage: (1) the SHA256 pre-check in `reproduce.sh` hard-codes the hash of `external_validation_sources.lock.json` itself, but the script also overwrites that file at the end of every `run()` call — meaning any online execution will change the lock file and break subsequent offline pre-checks without guidance; (2) the drift-scenario logs (`regex_drift_*.log`) reference a snapshot path `logs/regex_drift_snapshot.txt` that is not listed in the canonical `external_validation_sources.lock.json` and whose existence in the repository is not confirmed in the provided artifacts, making the drift negative-example replay non-self-contained. Additionally, the old-format fields in drift logs (`n_u0_membership_must`, `mutation_detected`, `expected_contradictory`) diverge from the current script's output schema, indicating the drift logs were produced by a prior code version and cannot be re-generated verbatim by the current script.

## Strengths
- Lock file covers all 9 source URLs with SHA256 + UTC timestamp + snapshot path, satisfying the stated source-lock semantics.
- reproduce.sh performs SHA256 pre-checks on both external_validation.py and external_validation_sources.lock.json before any execution, providing a tamper-evident entry point.
- Offline replay path in fetch_text() verifies each individual snapshot's SHA256 at load time, so per-file integrity is checked on every run.
- All four paper-claimed acceptance criteria are exactly satisfied in the graceful-may log: n_real_projects=3, raw_judgement_distribution={consistent:3,contradictory:0,inconclusive:0}, policy_judgement_distribution={consistent:3,contradictory:0,inconclusive:0}, mutation_detected_by_expectation=6.
- extraction_patterns field retains matched substrings for all 9 URL×layer combinations, providing an auditable trace of what regex matched what text.
- Three replay modes (fail-fast, graceful-must, graceful-may) are invoked in a single script with deterministic flag sets, satisfying the multi-mode documentation.
- Python stdlib-only dependency means no pip install step is needed, eliminating a common reproducibility failure mode.
- Mutation table in the log matches the paper's Table in §6.2 exactly (6/6 expectations satisfied, correct per-project intersection values).

## Required Fixes
- BLOCKER — lock file self-hash brittleness: reproduce.sh hard-codes the SHA256 of external_validation_sources.lock.json (071c48e1…), but run() unconditionally overwrites this file even in offline mode (main() always writes lock_path). An independent reviewer who runs the offline replay will have the lock file modified on disk after step [1/3], causing steps [2/3] and [3/3] to fail the pre-check silently or fail the SHA256 check if they re-run reproduce.sh. Fix: either (a) move the SHA256 pre-check to run before any Python invocation and do not re-check it between modes, or (b) suppress lock-file rewrite when --offline-lock is supplied, or (c) document explicitly that reproduce.sh must be invoked once per checkout and that the lock file will be overwritten.
- BLOCKER — regex_drift_snapshot.txt not self-contained: The drift negative-example logs (regex_drift_graceful_must.log, regex_drift_graceful_may.log, regex_drift_lock.json) reference snapshot_file='logs/regex_drift_snapshot.txt' with SHA256=0d2d319f… for the SQLite pragma URL, but this file is not included in the canonical snapshots/ directory listed in external_validation_sources.lock.json and its existence in the repository is not confirmed. Without this file, the drift scenario cannot be replayed offline. Fix: include logs/regex_drift_snapshot.txt in the repository and document how to invoke the drift replay (e.g., add a reproduce_drift.sh or a --offline-lock logs/regex_drift_lock.json invocation to reproduce.sh).
- Schema divergence in drift logs breaks claimed re-generation: drift logs use fields absent from the current script (n_u0_membership_must, n_u0_membership_may, mutation_detected, expected_contradictory, detected_contradictory) and are missing fields the current script produces (n_u0_support_indicator, mutation_detected_by_expectation, layer_status, support_ratio, etc.). This means the drift logs cannot be regenerated verbatim by the current external_validation.py. Fix: either regenerate the drift logs with the current script version and update reproduce.sh to invoke the drift replay, or add an explicit note in §6.4 that the drift logs were produced by a prior schema version and provide a regeneration command.

## Optional Fixes
- reproduce.sh could print the computed SHA256 of each log file after generation, making cross-machine verification trivial without manual hashing.
- The paper claims reproduce.sh SHA256=5f2bbef4… but reviewers cannot verify this without running sha256sum on the file; consider embedding a self-check (sha256sum --check) within the script or adding a separate checksum manifest.
- The check_consistent_edge_cases.log is referenced in §6.4 but not provided among the context files; confirm it is present in the repository and note its path in §7.5.
- avg_support_ratio is stored as a full float (0.7777777777777777) in the log but the paper rounds to 0.778; a rounding normalization step in the summary output would make machine-readable results directly comparable to paper text.
- For the zlib unit_mismatch mutation, policy_judgement=consistent (not contradictory) because [-1,0] is a valid interval; the paper's mutation table notes expectation_satisfied=true for bound_shrinkage criterion, but a reviewer unfamiliar with the two-criterion split could misread the log as a detection failure. A brief inline comment in the JSON (or a summary field) distinguishing uand_contradiction from bound_shrinkage criteria would improve audit clarity.
