## Summary
The core acceptance checks (n_real_projects==3, raw/policy judgement distributions all-consistent, mutation_detected_by_expectation==6) are executable by any reader using only Python's standard library and the bundled snapshots/lock file. The offline replay path is deterministic: SHA-256 is verified before extraction, network is not required, and the three log modes (fail-fast, graceful-must, graceful-may) are driven by a single shell script. The log output matches every numerical claim in §6.2 exactly. No blocker prevents an independent reader from reproducing the stated acceptance checks. Two minor issues remain: (1) the SHA-256 stated in §7.2 for external_validation.py must be re-verified against the shipped file, because any whitespace or line-ending difference will cause the inline assertion to fail silently or loudly; (2) the SQLite source URL contains an anchor fragment (#pragma_page_size) that is stripped by urllib before the HTTP request, so the snapshot slug and lock key will differ between runs if the URL is ever fetched online—this is harmless for offline replay but must be documented. A few optional improvements address long-term URL stability and zlib lower-bound construction logic (req_lower uses z_default instead of the documented 0, giving -1 rather than 0, which is inconsistent with the prose but does not affect the consistent judgement).

## Required Fixes
- Verify and re-state the SHA-256 of external_validation.py in §7.2 against the exact bytes of the shipped file. The inline Python assertion in §7.5 will raise AssertionError for any reader whose checkout has different line endings (e.g., CRLF on Windows) or trailing whitespace, silently making the 'SHA check' section unreproducible. Consider replacing the hardcoded hash check with a note that readers should compute and compare, or provide both CRLF and LF hashes.
- Document that the SQLite lock key 'https://www.sqlite.org/pragma.html#pragma_page_size' includes a URL fragment. Python's urllib.request strips the fragment before the HTTP GET, so online re-fetching will store the snapshot under the slug for the fragment-free URL while the lock key retains the fragment. The offline path works because the lock lookup uses the full URL string as key and the snapshot file is already present, but a reader who tries to re-fetch online will get a SHA-256 mismatch or a duplicate snapshot. Add a comment in fetch_text or the lock file explaining this behaviour.

## Optional Fixes
- The zlib requirement lower-bound is constructed as min(0, z_default) when req_found and z_default is available, yielding -1 (since Z_DEFAULT_COMPRESSION=-1). The manuscript prose says the requirement range is [0,9] from 'between 0 and 9', but the actual artifact lower is -1. The consistent judgement is unaffected (intersection becomes [-1,9]), but the discrepancy between the prose description and the computed value could confuse readers. Consider adding a comment in zlib_artifacts explaining that Z_DEFAULT_COMPRESSION is included as a valid sentinel, or tightening the lower bound to 0 when the requirement phrase is satisfied.
- The regex_drift_failure.log and regex_drift_graceful_{must,may}.log files are referenced in §6.4 but are not included in the provided context. Confirm these files exist in the repository; if they are generated by a separate script that is not part of reproduce.sh, add a one-line comment in reproduce.sh pointing to how to generate them, so the negative-example claims in §6.4 are also independently reproducible.
- For long-term archival, consider adding a Wayback Machine or DOI-backed fallback URL for each of the 9 locked sources (as already recommended in §7.5). Currently the lock only carries the primary URL; if that URL changes, the online re-fetch path breaks permanently.
- The manifest SHA-256 stated in §7.2 (lake-manifest.json: 8c098d...) should be mechanically verified in CI or reproduce.sh alongside the Python hash check, so Lean reproducibility and PoC reproducibility are tested in a single command.
