## Residual Required Fixes
- [R1] BLOCKING – §3.4 MUS definition is logically incomplete. `MUS(active)` is defined as `Inconsistent(active) ∧ ∀active', active' ⊊ active → ¬Inconsistent(active')`. However, `active' ⊊ active` as defined in the same section uses `∀i, active'(i) → active(i)` (downward subset), which means the minimality quantifies only over *strict subsets* expressed as predicates on ι. In a Lean4 setting where `ι` is an arbitrary type without decidable equality, enumerating all such `active'` is not straightforwardly well-typed, and the definition as given admits the vacuous case where no strict subset exists (e.g., ι a singleton). The manuscript asserts 'MUS抽出アルゴリズムの正当性証明は今後課題' but does not flag that the MUS *definition* itself needs a well-foundedness or finiteness assumption on active to be non-vacuous. Add a explicit side-condition: either `Fintype {i | active i}` or `∃i, active i ∧ ∃active', active' ⊊ active ∧ Inconsistent(active')` as a non-vacuousness guard, and note this in the Lean file reference.
- [R1] BLOCKING – §2.4 / §3.3 notational inconsistency in `UAndOn_antitone`. In §2.4 the Lean statement reads: `(hJK : ∀ i, J i → K i) : M.UAndOn K ⊆ M.UAndOn J`. In prose §3.3 the same theorem is described as 'active を増やすと U∧ は反単調に小さくなる'. The Lean statement has conclusion `UAndOn K ⊆ UAndOn J` when `J ⊆ K` (as predicates), meaning *larger* active set → *smaller* UAndOn — this is correct for the inclusion order on SpecSet. However, the prose says 'active を増やすと' (increasing active) gives a *smaller* U∧, which matches. The problem is that the naming convention in §2.4 names the *smaller* predicate `J` and the *larger* `K` (hJK : J ⊆ K), yet the conclusion uses `K` as the argument to the larger UAndOn and `J` as the result. A reader following the Lean statement directly reads 'if J implies K (J is smaller), then UAndOn(K) ⊆ UAndOn(J)' — this is correct but the variable naming `J`/`K` is the reverse of the usual mathematical convention (where the larger set is typically named with the later letter on the left). The inconsistency becomes a real ambiguity at §3.3 bullet '`UAndOn_antitone`: `active` を増やすと `U∧` は反単調に小さくなる（要件が厳しくなる）' — this is consistent with the Lean statement but the direction is implicit. Require: add a one-line explicit statement in §3.3 of the form 'formally: if J(i)→K(i) for all i then UAndOn(K)⊆UAndOn(J)' to make the direction unambiguous without forcing the reader to cross-reference the Lean snippet.
- [R1] BLOCKING – §6.2 dual-projection incoherence. The PoC explicitly introduces two separate observation functions: `proj_i^{U0} := interval_hat_i` (both-sided interval, returns none if either bound missing) and `measure_i^{U∧} := bounds_hat_i` (partial bounds, used by classify_uand). The manuscript acknowledges 'PoC は U0 側と U∧側で異なる観測関数を併置する運用構成である' and explicitly disclaims '∀x, classify_uand(bounds_hat(x)) ↔ x ∈ UAndOn の同値主張を行わない'. This is honest. However, the abstract model in §2 defines a *single* `proj_i : Ω → Option β_i` per layer, and both U0 and U∧ are defined using the *same* lifted(i) := preimage_i(A(i)). The PoC therefore does not instantiate the abstract model — it uses a *different* (richer) structure with two observation functions per layer. This gap must be explicitly formalized: either (a) extend the abstract model to allow U0 and U∧ to use different projections (a non-trivial change), or (b) clearly state in a prominently placed remark (not buried in the table footnote) that the PoC is a *two-projection operational approximation* that does not directly instantiate Model in §2, and that the theoretical results of §4 apply only under the assumption that both projections agree — an assumption that is not verified for the concrete regex extractor. As currently written, a reader can reasonably (but incorrectly) infer that the §6.2 PoC serves as a concrete instance of the §2 model.
- [R2] R1 (Terminology inconsistency — join/meet vs. specification strength): The paper fixes the lattice order as ⊆ in §2.3 and correctly states U0=∪ is weaker (more permissive) under that order. However, in prose elsewhere U0 is described as a 'unified' or 'integrated' specification, which readers from type-theory or lattice-theory backgrounds may read as 'stronger.' A single canonical boxed remark must be inserted at the first substantive use of U0 in §3.1 (or §0.2): 'Under the inclusion order ⊆, U0 = ∪ lifted(i) is the least upper bound (join) and therefore the weakest (most permissive) combined constraint — it is an over-approximation envelope, not a tightened specification.' Without this, the join/meet directionality is a persistent reader-misinterpretation risk.
- [R2] R2 (Publication-safety risk — conditional operational corollaries in §4.3 lack adequate demarcation from PoC context): §4.3 correctly states that adequacy theorems are for abstract relation E and applying them to a concrete extractor requires separately proving hSound/hComplete. However, the '運用上の帰結' (operational corollaries) block in §4.3 is presented without a clear warning that these corollaries do NOT apply to the PoC regex extractor in §6, because that extractor's hSound/hComplete are not proven. A reader reading §4.3 then §6 can conclude that the corollaries (e.g., 'sound side suppresses false consistency reports') apply to the PoC. Insert a clearly delimited WARNING block immediately before the 運用上の帰結 subsection: 'The following corollaries are conditional on hSound/hComplete holding for the extractor in use. These properties are NOT verified for the regex extractor in §6 (see §0.3 Non-goals and §4.8). Applying these corollaries to §6 results requires separate extractor proof obligations.'
- [R2] R3 (Understated gap between RQ2 contribution claim and trivial D(i) in all experiments): §0.2 frames RQ2 as 'can A(i) ⊆ D(i) be lifted to root witness validity?' implying this is a demonstrated contribution. §2.1 provides extensive motivation for D(i)/A(i) separation. Yet §6.2 discloses that D(i) = ℤ×ℤ (trivial) throughout all PoC experiments, and the Non-goals list in §0.3 does not mention this gap. RQ2 is answered only at the theory/Lean level; the D(i) separation is never exercised concretely. Add to §0.3 Non-goals: 'D(i) separation is modeled and type-checked in Lean but D(i) is set to the trivial domain (ℤ×ℤ) in all PoC experiments; empirical validation of domain-constrained D(i) (unit normalization, type-domain constraints) is deferred to future work.' This prevents readers from overinterpreting RQ2 as empirically demonstrated.
- [R2] R4 (Ambiguous mutation detection in table — heterogeneous detection criteria presented uniformly): The §6.2 mutation table shows expectation_satisfied=true for all 6 mutations, but the detection criteria are heterogeneous: stale_requirement_lower mutations are detected by raw_judgement==contradictory (U∧ detection), while unit_mismatch_upper_scale_down_1024 mutations are detected by upper' <= floor(upper/1024) (bound shrinkage criterion, not U∧ contradiction). The zlib unit_mismatch row has mutated_intersection=[-1,0] which is a valid interval (consistent, not contradictory), yet is reported as 'detected.' The claim mutation_detected_by_expectation=6 (out of 6) is technically correct but conflates two qualitatively different detection mechanisms. Add a 'detection_method' column to the table with values 'U∧ contradiction' or 'bound_shrinkage_criterion', and add a footnote: 'Not all detections indicate U∧ inconsistency; unit_mismatch detections use a bound-shrinkage criterion that may be satisfied even when raw_judgement=consistent.'
- [R3] Verify and re-state the SHA-256 of external_validation.py in §7.2 against the exact bytes of the shipped file. The inline Python assertion in §7.5 will raise AssertionError for any reader whose checkout has different line endings (e.g., CRLF on Windows) or trailing whitespace, silently making the 'SHA check' section unreproducible. Consider replacing the hardcoded hash check with a note that readers should compute and compare, or provide both CRLF and LF hashes.
- [R3] Document that the SQLite lock key 'https://www.sqlite.org/pragma.html#pragma_page_size' includes a URL fragment. Python's urllib.request strips the fragment before the HTTP GET, so online re-fetching will store the snapshot under the slug for the fragment-free URL while the lock key retains the fragment. The offline path works because the lock lookup uses the full URL string as key and the snapshot file is already present, but a reader who tries to re-fetch online will get a SHA-256 mismatch or a duplicate snapshot. Add a comment in fetch_text or the lock file explaining this behaviour.
