## Residual Required Fixes
- [R2] BLOCKER-1 (Claim-scope asymmetry in mutation detection summary): The abstract-level summary reports `mutation_detected_by_expectation = 6 (out of 6)` as a single aggregated figure, but the two mutation types have fundamentally different detection semantics: `uand_contradiction` tests U∧ emptiness (a direct model-theoretic check), while `bound_shrinkage` tests a numeric inequality on extracted bounds (an operational artifact with no model-theoretic grounding proven in this paper). Aggregating them under one 'detected' count implies equivalent epistemic status. Required fix: either report the two counts separately (3 + 3) with distinct framing, or add a sentence immediately adjacent to the aggregate figure clarifying that the two criteria differ in their relationship to the formal model. This is a precision issue that a reviewer in formal methods will flag as conflating proven and unproven detection claims.
- [R2] BLOCKER-2 (Warning placement inversion in §4.3): The 'IMPORTANT (applicability boundary)' and 'WARNING (PoC non-applicable)' blocks appear *after* the adequacy theorem list in the document's linear read order. A reader who encounters the theorems before the warnings may read the subsequent proof obligation list as guidance for applying the theorems to the PoC, not as a statement that the application was not done. The fix is to move the warning blocks to *before* the theorem enumeration, or to restructure §4.3 so that the abstract theorem statement and the non-application disclaimer appear as a unit before any theorem names are introduced. As currently ordered, this inverts the intended protective function of the disclaimers.
- [R2] BLOCKER-3 (Circularity risk in `U0_support ↔ U0` equivalence claim): §6.2 states 'supported_i(x) ↔ x∈lifted(i)' holds under the PoC instantiation, and from this derives 'U0_support(x) ↔ x∈U0 (must interpretation)'. However, `supported_i(x)` is defined as `∃p, interval_hat_i(x)=some(p) ∧ p∈A_i`, and `lifted(i)` is `preimage_i(A_i)` which expands to `∃y, proj_i(x)=some(y) ∧ y∈A_i`. The equivalence holds only if `interval_hat_i = proj_i^{U0}` by definition—which is stated but the definitional equality is given in running prose rather than as a boxed definition. A reviewer will ask: is this equivalence a theorem or a definition? If it is a definition (i.e., `proj_i^{U0} := interval_hat_i` by fiat), say so explicitly with a labeled definition box. If it is a theorem, provide the proof. Without this, the equivalence claim appears to borrow formal credibility from the Lean-verified `preimage` while the Lean verification does not cover the extractor chain.
- [R3] BLOCKER — lock file self-hash brittleness: reproduce.sh hard-codes the SHA256 of external_validation_sources.lock.json (071c48e1…), but run() unconditionally overwrites this file even in offline mode (main() always writes lock_path). An independent reviewer who runs the offline replay will have the lock file modified on disk after step [1/3], causing steps [2/3] and [3/3] to fail the pre-check silently or fail the SHA256 check if they re-run reproduce.sh. Fix: either (a) move the SHA256 pre-check to run before any Python invocation and do not re-check it between modes, or (b) suppress lock-file rewrite when --offline-lock is supplied, or (c) document explicitly that reproduce.sh must be invoked once per checkout and that the lock file will be overwritten.
- [R3] BLOCKER — regex_drift_snapshot.txt not self-contained: The drift negative-example logs (regex_drift_graceful_must.log, regex_drift_graceful_may.log, regex_drift_lock.json) reference snapshot_file='logs/regex_drift_snapshot.txt' with SHA256=0d2d319f… for the SQLite pragma URL, but this file is not included in the canonical snapshots/ directory listed in external_validation_sources.lock.json and its existence in the repository is not confirmed. Without this file, the drift scenario cannot be replayed offline. Fix: include logs/regex_drift_snapshot.txt in the repository and document how to invoke the drift replay (e.g., add a reproduce_drift.sh or a --offline-lock logs/regex_drift_lock.json invocation to reproduce.sh).
- [R3] Schema divergence in drift logs breaks claimed re-generation: drift logs use fields absent from the current script (n_u0_membership_must, n_u0_membership_may, mutation_detected, expected_contradictory, detected_contradictory) and are missing fields the current script produces (n_u0_support_indicator, mutation_detected_by_expectation, layer_status, support_ratio, etc.). This means the drift logs cannot be regenerated verbatim by the current external_validation.py. Fix: either regenerate the drift logs with the current script version and update reproduce.sh to invoke the drift replay, or add an explicit note in §6.4 that the drift logs were produced by a prior schema version and provide a regeneration command.
