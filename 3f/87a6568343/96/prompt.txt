# Architecture Reorganization Plan: specd as UDA/f Core Engine

## Context - Corrected Understanding

### Clarification: SpecRepository and UDAFModel are NOT Duplicates

**Critical correction**: SpecRepository and UDAFModel serve DIFFERENT purposes and are BOTH necessary.

#### Correct Understanding of the Architecture

**SpecRepository** (spec-core/src/data/repository.rs):
- **Role**: Data persistence layer (Storage/Retrieval)
- **Responsibility**: Save/load specifications to/from disk (JSON, YAML, database)
- **Interface**: CRUD operations (add_node, get_node, list_nodes, etc.)
- **Format**: Graph structure (petgraph) - optimized for storage and retrieval
- **Analogy**: Like a database ORM - handles data persistence

**UDAFModel** (spec-core/src/formal/model/mod.rs):
- **Role**: Formal verification layer (In-memory analysis)
- **Responsibility**: Perform formal verification using Z3 SMT solver
- **Interface**: Verification operations (verify_consistency, prove_implication, etc.)
- **Format**: Semantic structure (HashMap) - optimized for formal reasoning
- **Analogy**: Like a business logic layer - handles domain operations

**ModelSync** (spec-core/src/formal/model/sync.rs):
- **Role**: Bridge between persistence and verification
- **Responsibility**: Load data from SpecRepository → Build UDAFModel for verification
- **Flow**: Disk → SpecRepository → ModelSync → UDAFModel → Verification → Results

#### Why Both Are Necessary

```
User Request: "Verify this specification is consistent"
     ↓
1. Load from disk
   SpecRepository.load() → reads JSON/YAML files
     ↓
2. Build verification model
   ModelSync.sync_from_repository() → constructs UDAFModel in memory
     ↓
3. Perform verification
   UDAFModel.verify_consistency() → runs Z3 solver
     ↓
4. Save results
   ModelSync.export_proof_metadata() → updates SpecRepository
   SpecRepository.save() → writes back to disk
```

**This is NOT duplication** - it's a standard layered architecture:
- **Persistence layer** (SpecRepository) - How data is stored
- **Domain layer** (UDAFModel) - How data is reasoned about

**How specifications are currently stored and verified**:


- ✅ ModelSync bridges between them
- ✅ No duplication - they serve different purposes

## Proposed Solution: Proto API Abstraction Level

### Problem Statement

The current proto exposes TWO different abstraction levels:

1. **Low-level operations (28 RPCs)**: Node/Edge manipulation
   - AddNode, GetNode, ListNodes, RemoveNode
   - AddEdge, ListEdges, RemoveEdge
   - SetUniverse, FilterByLayer
   - etc.

2. **High-level operations (26 RPCs)**: UDA/f concepts
   - CreateUniverse, GetUniverse, ListUniverses, DeleteUniverse
   - CreateDomain, GetDomain, ListDomains
   - CreateAdmissibleSet, VerifyConsistency, VerifyImplication
   - CreateTransform, VerifyTransformSoundness
   - ConstructU0 (reverse mapping)

**The issue**: Exposing Node/Edge operations violates the principle that **specd should manage the formal world using UDA/f concepts**.

**User's insight**: "Node/Edgeってなんですか？...それはNode/Edgeなのですか？"
- Node/Edge are **implementation details** of SpecRepository
- They should be **internal to specd**, not exposed via proto

### Recommendation

**Keep the current architecture** (SpecRepository + UDAFModel):
- ✅ SpecRepository continues to handle persistence (using Node/Edge internally)
- ✅ UDAFModel continues to handle verification (using Z3)
- ✅ ModelSync continues to bridge between them

**Change only the proto API**:
- ❌ Remove or deprecate 28 Node/Edge RPCs from public proto
- ✅ Keep 26 UDA/f concept RPCs + 6 Project RPCs
- ✅ Clients work exclusively with UDA/f concepts (Universe, Domain, AdmissibleSet, Transform)

### Implementation Approach

**Phase 1: Mark Node/Edge RPCs as deprecated** (backward compatible)
- Add deprecation annotations to proto
- Update proto comments: "DEPRECATED: Use UDA/f operations instead"
- Keep implementations working for 2-3 releases

**Phase 2: Update spec-cli to use UDA/f operations**
- Migrate all commands to use CreateUniverse, CreateDomain, etc.
- Remove dependency on Node/Edge operations
- `spec add "..."` → calls `CreateAdmissibleSet` instead of `AddNode`

**Phase 3: Remove deprecated RPCs** (breaking change, next major version)
- Remove Node/Edge RPC definitions from proto
- Remove implementations from specd
- Node/Edge operations become purely internal to SpecRepository

### Internal Implementation Details

**How specd implements UDA/f RPCs using SpecRepository**:

```rust
// Example: CreateAdmissibleSet RPC
pub async fn create_admissible_set(
    &self,
    req: CreateAdmissibleSetRequest,
) -> Result<CreateAdmissibleSetResponse> {
    let project = self.project_manager.load_project(&req.project)?;

    // 1. Add to UDAFModel (verification layer)
    let spec_id = project.udaf_model.create_admissible_set(
        req.constraints,
    )?;

    // 2. Save to SpecRepository (persistence layer) - INTERNAL use of Node
    project.repository.add_node(SpecNodeData {
        id: spec_id.clone(),
        content: format!("{:?}", req.constraints),
        kind: SpecNodeKind::AdmissibleSet,
        formality_layer: 0,
        metadata: HashMap::new(),
    })?;

    // 3. Save to storage
    self.project_manager.save_project(&project)?;

    // 4. Return UDA/f concept (not Node details)
    Ok(CreateAdmissibleSetResponse {
        admissible_set: Some(AdmissibleSet {
            spec_id,
            constraints: req.constraints,
            contradicts: vec![],
            metadata: HashMap::new(),
        }),
    })
}
```

**Key insight**: Node/Edge operations are called **internally by specd** when implementing UDA/f RPCs, but **clients never see them**.
