# Implementation Plan: UDA Model Minimization + Proof Mechanisms

## Context

### Problem 1: UDA Model is Not Minimized

Current UDAF structures mix three concerns without clear separation:
1. **Identity** (IDs for entity identification)
2. **Proof-essential data** (constraints, relationships needed for formal verification)
3. **Metadata** (human-readable names, descriptions, organizational info)

**Analysis shows**:
- **Universe**: NO proof-essential fields (only organizational)
- **Domain**: `covered_by` is proof-essential; `name`, `description` are metadata
- **AdmissibleSet**: `constraints`, `contradicts` are proof-essential; `name`, `universe_id` are metadata
- **Prover currently accesses metadata unnecessarily** - should only see IDs + proof data

### Problem 2: Prover Doesn't Use D and U Properly

The current Prover implementation only uses AdmissibleSet (A) for proofs, completely ignoring Domain (D) and Universe (U). This violates the theoretical foundation of the UDA/f model:

- **Contradiction proofs** currently check `A1 ∩ A2 ≠ ∅` but should check `A1 ∩ A2 ∩ D ≠ ∅` (within domain)
- **Leak detection** requires U (for leak A) and D (for leak B) but these are not used
- **仕様はAの要素であり、Dがなければ定まらない** - specification cannot be determined without D

The user has confirmed that while the broad concept is correct, we need to determine:
1. Can these proofs actually be implemented?
2. How should they be implemented?

### Investigation Results

**Technical Feasibility:**
- ✅ **Implication (A1 ⊆ A2)**: Fully feasible with current Z3 infrastructure
- ⚠️ **Completeness (D ⊆ D_S)**: Feasible IF Domain is formalized as constraints
- ⚠️ **Underspecification (leak A)**: Only heuristically detectable (not formally provable)
- ❌ **TransformSoundness**: Not feasible with current architecture (deferred)

**Core Challenge:**
- D (Domain) is currently only a natural language description, not a formal set
- U (Universe) has no formal boundary definition, only organizational structure
- **Key insight**: 漏れA（未規定）は設計上の選択であり、証明不可能。ヒューリスティック検出のみ可能。

## Solution: Two-Phase Refactoring

### Phase A: Minimize UDA Model (3-Layer Separation)
### Phase B: Implement Proof Mechanisms Using Minimized Model

## Phase A: UDA Model Minimization

### Design: Composition-Based 3-Layer Structure

Each UDAF entity (Universe, Domain, AdmissibleSet) is restructured into:
1. **Identifier field** (ID only)
2. **ProofData struct** (only proof-essential fields)
3. **Metadata struct** (everything else)

**Benefits**:
- Clear separation of concerns at struct level
- Prover can accept only `&ProofData`, never metadata
- Compile-time enforcement of layer boundaries
- Minimal migration impact (composition, not replacement)

## Phase B: Implement Proof Mechanisms

(Using minimized UDA model from Phase A)

## Approach: Hybrid Formalization

### 1. Domain Formalization (Already in Phase A)

**Domain.proof_data.constraints** added in Phase A minimization:
```rust
pub struct DomainProofData {
    pub constraints: Vec<Constraint>,  // Formal domain boundaries
    pub covered_by: SpecSet,
}
```

**Rationale**: Hybrid approach allows:
- Optional formalization: `constraints` can be empty
- Graceful degradation when D not formalized (falls back to A-only proofs)
- Progressive enhancement as specifications mature
- Clear separation: constraints in proof_data, description in metadata

### 2. Three Categories of Proof Implementation

#### Category A: Formal Proofs (Z3-based) ✅

**1. Implication: A1 ⊆ A2**
- Formula: `UNSAT(A1 ∧ ¬A2)`
- Interpretation: Every implementation satisfying A1 also satisfies A2
- Implementation: `prove_implication(A1, A2) -> Proof`
- Status: **Highly feasible** - works with current Z3Backend

**2. Consistency Within Domain: A1 ∩ A2 ∩ D ≠ ∅**
- Formula: `SAT(A1 ∧ A2 ∧ D)`
- Interpretation: Specifications are consistent within the domain
- Implementation: `prove_consistency_within_domain(A1, A2, D) -> Proof`
- Graceful degradation: If `D.constraints.is_empty()`, falls back to current `prove_consistency(A1, A2)`

**3. Completeness: D ⊆ D_S**
- Formula: `UNSAT(D ∧ ¬(A1 ∨ A2 ∨ ... ∨ An))`
- Interpretation: Every element of domain is covered by some specification
- Implementation: `prove_completeness(D, [A1, A2, ...An]) -> Proof`
- Detects **漏れB（カバレッジ不足）**
- Requires: D must be formalized

#### Category B: Heuristic Analysis ⚠️

**4. Underspecification Detection (Leak A)**
- **Cannot be formally proven** - underspecification is a design choice, not an error
- Heuristics: constraint count, free variables, domain keyword matching
- Implementation: `detect_underspecification(A, D, U) -> UnderspecificationReport`
- Returns: Confidence score (0.0-1.0), reasons, suggestions
- Detects **漏れA（未規定）**

#### Category C: Future Work ❌

**5. TransformSoundness: f(A_source) ⊆ A_target**
- Requires formal semantics of transform functions
- Current architecture uses opaque strategy patterns (ASTAnalysis, NLPInference, etc.)
- Not feasible without major architectural changes
- **Explicitly deferred to future work**

## Key Decisions & Rationale

### Why Optional Domain.constraints?

**Decision**: Make Domain.constraints optional (empty Vec by default)

**Rationale**:
- Many domains are defined informally (natural language only)
- Forcing formalization would be impractical
- Graceful degradation allows system to work at all maturity levels
- Progressive enhancement: users can formalize domains as specs mature

### Why Not Prove Underspecification?

**Decision**: Underspecification detection is heuristic, not a formal proof

**Rationale**:
- 漏れA（未規定）は設計上の選択であり、エラーではない
- "Too wide" is subjective - depends on intended design space
- Cannot formally define "correct width" of admissible set
- Heuristics provide useful guidance without false certainty

### Why Defer TransformSoundness?

**Decision**: Explicitly defer TransformSoundness to future work

**Rationale**:
- Requires formal semantics of transform functions
- Current architecture uses opaque strategies (ASTAnalysis, NLPInference)
- Would need major architectural changes (symbolic execution, program synthesis)
- Not critical for core UDA-based proof mechanisms
